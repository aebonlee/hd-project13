# 개발일지 — J1939 CAN 사양 정리 자동화 (hd-project13)

기획: 안상욱 (HD건설기계, 전기전자검증팀) · 생성형 AI 업무자동화 전문가과정 1차수

> ⚠ **이 일지는 뒤늦게 쓴 것이다.**
> 첫 구현이 끝난 뒤에 저장소를 되짚어 적었다. §1~§4 는 첫 커밋 메시지와
> 코드·테스트에 남아 있는 근거를 옮긴 것이고, §5~§6 은 그 뒤 작업이라
> 직접 겪은 것이다. **첫 구현 때 무엇을 시도했다가 버렸는지는 기록이
> 남아 있지 않아 적지 않았다** — 지어내면 다음 사람이 그것을 사실로 믿는다.

---

## 1. 문제는 양식이 아니라 '조용히 틀리는 것'이었다

전장품마다 사양서가 따로 온다. 업체마다 양식이 다르고 형식도 Word·PDF·Excel 로
제각각이다. 그래서 첫인상은 "여러 양식을 읽는 파서를 만드는 일"이다.

그런데 진짜 위험한 것은 못 읽는 것이 아니다. **잘못 읽고도 표가 멀쩡해 보이는 것**이다.
CAN 사양이 한 줄 틀리면 그 표를 믿고 개발한 전장품이 통신하지 못한다.
그때 표를 다시 봐도 어디가 틀렸는지 알 수 없다.

그래서 이 도구의 규칙은 대부분 **"모를 때 어떻게 하느냐"**에 대한 것이다.

## 2. ID 를 지어내지 않는다

ID 안에 PGN 이 들어 있다. 그래서 ID 만 있으면 PGN·SA·우선순위를 계산해 채울 수 있다.

반대는 안 된다. PGN 만 있을 때 우선순위 6 을 가정하면 **그럴듯한 ID** 가 나온다.
계산이 맞아 보이고 표도 채워진다. 그런데 그 값은 사양이 아니라 추측이다.

한 번 엑셀에 들어가면 다음 사람은 그것을 실제 사양으로 믿고 쓴다.
그래서 비워 둔다. 화면에도 왜 비었는지 적는다 —
*"우선순위와 SA 를 알 수 없어 ID 를 만들 수 없으므로 비워 두었습니다."*

계산으로 채운 값에는 **「계산」 표시**를 단다. 문서에 적혀 있던 값과
신뢰도가 다르기 때문이다. 엑셀에도 「계산으로 채운 항목」 열로 남는다.

## 3. 어긋난 사양서를 고쳐 주지 않는다

ID 와 PGN 이 **둘 다** 적힌 사양서가 있다. 사람이 손으로 옮기다 한쪽만 고치면
둘이 어긋나는데, 그대로 정리하면 틀린 표가 만들어진다.

계산해 맞춰 보고 어긋나면 「검토필요」에 **양쪽 값을 다 적어** 알린다.
고쳐 주지 않는 이유는 **어느 쪽이 맞는지 원본을 봐야 알기 때문**이다.
계산값으로 덮으면 문서가 틀린 것인지 우리가 틀린 것인지 아무도 모르게 된다.

잡아내는 것: PGN·SA·우선순위가 ID 계산값과 다름 / CAN 채널이 1~3 밖 /
신호가 데이터 길이를 넘음 / 시작비트를 0 부터 센 문서(J1939 는 1 부터).

## 4. 못 알아본 열을 추측해 붙이지 않는다

업체마다 열 이름이 다르다. 「CAN ID」·「Identifier」·「메시지 ID」가 같은 자리다.
`js/mapping.js` 의 `ALIASES` 가 흡수한다.

여기서도 같은 규칙이다. **못 알아본 열은 끌어다 붙이지 않는다.**
엉뚱한 열을 ID 로 잘못 보면 표 전체가 조용히 틀린다.
새 양식이 들어오면 코드가 아니라 `ALIASES` 에 이름만 더한다.

### 세 형식, 한 코드

Word 는 ZIP 이라 브라우저 내장 `DecompressionStream` 으로 푼다 —
압축 라이브러리를 들이지 않았다. PDF 는 글자 **좌표**로 줄과 칸을 복원한다.
셋 다 표로 만든 뒤는 같은 코드를 쓴다.

PDF 에 한글이 있으면 CMap 이 필요하다. 없으면 한글이 **빈 문자열**이 되어
"표가 없다"로 끝난다 — 실패가 아니라 **빈 성공**으로 보이는 유형이라 더 나쁘다.
`lib/cmaps/` 를 함께 두는 이유다.

### 예제를 일부러 다르게 만들었다

셋이 같으면 한 가지만 맞춰도 통과해 검사가 의미를 잃는다.
A사는 ID 만, B사는 PGN·SA·채널만(+CAN 표가 아닌 부속 표), C사는 다 있되
한 줄이 일부러 어긋나 있다.

### 깨뜨려서 확인했다

첫 커밋에 기록이 남아 있다. 규칙을 하나씩 일부러 어겨 보고 테스트가 잡는지 봤다 —
PDU1 에서 PS 를 PGN 에 넣기 / 어긋난 PGN 을 조용히 넘기기 / 못 알아본 열을
추측해 붙이기 / PGN 만으로 ID 지어내기 / SA 를 10진으로 읽기 / 채널 범위 검사 빼기.
전부 잡혔다.

## 5. CI 를 붙였다

`test/logic.test.js` 에 31개가 있었지만 **사람이 손으로 돌려야 했다.**
안 돌리면 없는 것과 같다.

다른 프로젝트 저장소의 워크플로에서 `supabase/`·`scripts/sqltest/` 단계를 뺐다 —
이 저장소에는 없다. **있는 것만 돈다.** 의존성이 없어 `npm install` 단계도
두지 않았다. 파일을 열면 그대로 도는 것이 이 저장소의 전제다.

## 6. 화면 연기 테스트 — 두 번 틀렸고 둘 다 테스트 쪽이었다

규칙 31개가 전부 통과해도 `app.js` 의 오타 하나면 페이지가 빈 화면이 된다.
규칙은 맞는데 아무도 그것을 볼 수 없는 상태다. 파일을 읽어서는 안 잡힌다.

「예제 사양서로 해보기」 단추 하나가 xlsx·docx·pdf 세 파서를 모두 지나가므로
그것을 누르는 것이 가장 넓게 훑는 길이었다.

**하나.** `<input type=file>` 이 보이는지 확인했는데 css 로 감춰져 있었다.
사람이 보고 누르는 것은 `.drop` 라벨이다. 앱이 아니라 단언이 틀렸다.

**둘.** 테스트가 **30초를 기다린 끝에 시간 초과로만** 끝났다.
무엇이 잘못됐는지 한 마디도 나오지 않았다.

원인은 테스트가 띄우는 정적 서버가 `.mjs` 를 `octet-stream` 으로 내준 것이었다.
브라우저는 모듈 스크립트의 MIME 을 **엄격히 검사해 실행을 거부한다.**
이 앱은 PDF 를 `lib/pdf.min.mjs` 로 읽으므로 통째로 멈췄다.

MIME 표에 `.mjs` 와 `.bcmap`(한글 CMap)을 넣어 고쳤다. 그리고 **같은 일이 또
생기면 시간 초과 대신 무엇이 안 나왔는지 말하도록** 진단을 붙였다 —
화면에 뜬 글자, 서버가 못 내준 파일, 콘솔 오류를 함께 적는다.
테스트가 왜 실패했는지 모르는 상태가 실패 자체보다 나쁘다.

**깨뜨려서 확인했다.** `innerHTML` 을 `innerHTMLL` 로 바꾸니
`예제를 눌러 표가 그려진다` 가 원인 문구와 함께 실패했다.

## 8. 남은 것

- **기획서 원문이 없다.** `CLAUDE.md` 부록 A 가 비어 있다.
  지금 적힌 지시서는 구현에서 되짚은 것이라, **기획자가 요구했지만 구현되지 않은
  항목은 거기 없을 수 있다.** 원문을 받으면 대조해야 한다.
- **문장으로 적힌 사양** — 사양서 대부분이 표라 표부터 했다.
- **스캔한 PDF** — 글자층이 없어 못 읽는다. OCR 이 필요하다.
- **새 업체 양식** — `mapping.js` 의 `ALIASES` 에 이름을 더한다. 코드는 고치지 않는다.
