# J1939 CAN Protocol 사양 정리 자동화

> 🌐 **[aebonlee.github.io/hd-project13](https://aebonlee.github.io/hd-project13/)** · 저장소: https://github.com/aebonlee/hd-project13
> 기획: **안상욱** (전기전자검증팀) · 생성형 AI 업무자동화 전문가과정 1차수

건설장비 **모델별 CAN 사양**을 관리해야 하는데, 사양은 **전장품별로 따로** 들어옵니다.
업체마다 양식이 다르고 형식도 Word·PDF·Excel 로 제각각입니다.

이 도구는 그 사양서를 올리면 **정해진 CAN 양식으로 뽑아 엑셀 한 장**으로 모읍니다.

## 정리하는 다섯 가지

| 항목 | 형식 | 예 |
|---|---|---|
| **ID** | 16진 7~8자리 | `0x18F00401` · `0xCF00400` |
| **PGN** | 16진 4자리 | `E000` · `F029` · `FDD8` |
| **CAN Channel** | 1~3 (10진) | `2` |
| **Source Address** | 16진 2자리 | `21` · `44` · `5A` |
| **Period** | ms | `100` · `1000` · 요청 시 |

## 하나만 있어도 정리됩니다

사양서에 다섯 가지가 다 있는 일은 드뭅니다. **보통 ID 나 PGN 중 하나만** 적혀 있습니다.

**ID 가 PGN 보다 상위입니다 — ID 안에 PGN 이 들어 있습니다.**

| 사양서에 있는 것 | 채울 수 있는 것 | 비고 |
|---|---|---|
| ID | PGN · Source Address · 우선순위 | ID 를 뜯으면 그 안에 다 있습니다 |
| PGN | — | 우선순위와 SA 를 모르므로 **ID 는 만들지 않습니다** |
| CAN Channel · Period | — | 계산으로 얻을 수 없습니다 |

### 왜 ID 를 지어내지 않는가

PGN 만 있을 때 우선순위 6 을 가정하면 그럴듯한 ID 가 나옵니다.
그런데 그 값은 **사양이 아니라 추측**입니다.
한 번 엑셀에 들어가면 다음 사람은 그것을 실제 사양으로 믿고 씁니다.
그래서 비워 둡니다. `test/logic.test.js` 가 이 규칙을 지킵니다.

계산으로 채운 값에는 **「계산」 표시**가 붙고, 엑셀에도 「계산으로 채운 항목」 열로 남습니다 —
문서에 적혀 있던 값과 신뢰도가 다르기 때문입니다.

## 어긋난 사양서는 고치지 않고 알립니다

ID 와 PGN 이 **둘 다** 적힌 사양서가 있습니다.
사람이 손으로 옮기다 한쪽만 고치면 둘이 어긋나는데, 그대로 정리하면 틀린 표가 만들어집니다.

계산해 맞춰 보고 어긋나면 「검토필요」에 **양쪽 값을 다 적어** 알립니다.
어느 쪽이 맞는지는 원본을 봐야 알기 때문에 **고쳐 주지 않습니다.**

잡아내는 것:
- PGN 이 ID 계산값과 다름
- Source Address 가 ID 계산값과 다름
- 우선순위가 ID 계산값과 다름
- CAN Channel 이 1~3 이 아님
- 신호가 데이터 길이(DLC)를 넘어감
- 시작비트를 0 부터 센 문서 (J1939 는 1 부터)

## 세 형식을 어떻게 읽나

| 형식 | 방법 |
|---|---|
| **Excel** | SheetJS 로 시트마다 표를 읽습니다 |
| **Word** | `.docx` 는 ZIP 입니다. 브라우저 내장 `DecompressionStream` 으로 풀어 `word/document.xml` 의 표를 읽습니다 — **압축 라이브러리를 쓰지 않습니다** |
| **PDF** | pdf.js 로 글자와 **좌표**를 받아, y 가 비슷한 것끼리 한 줄로 묶고 머리글의 x 위치로 칸을 가릅니다 |

셋 다 표로 만든 뒤는 **같은 코드**를 씁니다 — 머리글 찾기(`mapping.js`)와 값 채우기(`j1939.js`).

> **PDF 에 한글이 있으면 CMap 이 필요합니다.** 내장되지 않은 CID 글꼴로 그린 사양서가 흔한데,
> CMap 없이 읽으면 한글이 **빈 문자열**로 나와 "표가 없다"고 나옵니다.
> `lib/cmaps/` 를 함께 두는 이유입니다.

## 업체마다 다른 열 이름

`js/mapping.js` 의 `ALIASES` 가 흡수합니다. 「CAN ID」·「Identifier」·「메시지 ID」를 같은 자리로 모읍니다.

**못 알아본 열은 끌어다 붙이지 않습니다.** 엉뚱한 열을 ID 로 잘못 보면 표 전체가 조용히 틀립니다.
새 양식이 들어오면 `ALIASES` 에 이름만 추가하면 됩니다 — 코드는 고치지 않습니다.

## 파일은 서버로 올라가지 않습니다

읽기도 엑셀 만들기도 전부 브라우저 안에서 끝납니다.
사내 사양서를 다루는 도구라 이 점이 중요합니다.

## 실행·검사

```bash
# 단위 테스트 (ID↔PGN 계산, 표기 규칙, 열 이름 맞추기)
node test/logic.test.js

# 예제 사양서 다시 만들기 (양식이 서로 다른 3종)
python3 scripts/make_samples.py
```

예제는 일부러 서로 다르게 만들었습니다 — 셋이 같으면 한 가지만 맞춰도 통과해 검사가 의미를 잃습니다.

| 예제 | 특징 |
|---|---|
| `A사_…xlsx` | **ID 만** 있음 → PGN·SA 를 계산해야 함 |
| `B사_…docx` | **PGN·SA·채널만** 있음 → ID 를 지어내면 안 됨. CAN 표가 아닌 부속 표도 섞여 있음 |
| `C사_…pdf` | 다섯 항목 다 있음. 영문 머리글 + **한 줄이 일부러 어긋나 있음** |

## 앞으로

- 표가 아니라 **문장으로 적힌 사양**은 아직 못 읽습니다. 사양서 대부분이 표라 표부터 했습니다.
- 스캔한 PDF(이미지)는 글자층이 없어 못 읽습니다. OCR 이 필요합니다.
- 모델·전장품을 파일명에서 추측하지 않습니다. 사양서 안에 열로 있으면 담고, 없으면 비웁니다.
